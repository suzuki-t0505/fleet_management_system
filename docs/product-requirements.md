# プロダクト要求定義書 (Product Requirements Document)

## プロダクト概要

### 名称

**Fleet Management System** - 運送事業者向け 車両・運行記録管理システム

### プロダクトコンセプト

- **紙とExcelの台帳を1つのWebシステムに集約**: 車両台帳・運転者台帳・運行日報・点検整備記録を単一のデータベースで一元管理し、拠点ごとに散在する台帳の二重管理をなくす
- **期限とリスクを「思い出す」必要をなくす**: 車検・保険・法定点検の期限をシステムが監視し、期限超過が起きる前に運行管理者へ通知する
- **現場が入力し、管理者が活用する**: 運転者はスマートフォンから最小限の入力で日報・ヒヤリ報告を登録し、運行管理者はその蓄積を安全管理と車両稼働の改善に使う

### プロダクトビジョン

運送事業者の車両管理業務は、拠点ごとのExcelと紙のバインダーに分断されている。車検切れの直前発覚、日報の転記作業、事故・ヒヤリ情報が拠点内に留まり全社の再発防止につながらない――これらはすべて「記録が1か所にないこと」から生じている。

本システムは、車両・運転者・運行・点検・事故の記録を1つのシステムに集約し、拠点をまたいだ横断的な把握を可能にする。運行管理者は台帳の突合や期限確認といった作業から解放され、安全管理と稼働改善という本来の業務に時間を使える。

まずは自社（車両約300台・5〜10拠点）の業務をこのシステムに載せきることを目標とする。

### 目的

- 拠点ごとに分散した車両台帳・運転者台帳を全社単一のマスタに統合する
- 運行日報を運転者自身が当日中にデジタル入力する運用を確立し、転記作業を廃止する
- 車検・保険・法定点検の期限超過をゼロにする
- 事故・ヒヤリハットを全社で共有し、改善報告までを1つのフローで完結させる
- 拠点階層に沿った権限分離により、他拠点データへの不要なアクセスを防ぐ

### 技術前提

- Elixir / Phoenix LiveView / PostgreSQL / Tailwind CSS（開発・実行環境は Docker）
- 自社向け**単一テナント**構成（マルチテナントSaaS化は本PRDのスコープ外）
- 詳細は `docs/architecture.md`（別途作成）および `docs/coding-rules.md` を参照

## ターゲットユーザー

本システムの利用者は3ロール。組織は「本社 - 拠点（営業所）」の階層を持ち、データは拠点単位でスコープされる。

### プライマリーペルソナ: 佐藤健一（45歳、営業所の運行管理者）

- 車両40台・運転者35名を擁する営業所に所属。運行管理者資格を保有
- 現在の業務ツール: Excel（車両台帳・点検記録）、紙の運行日報、Googleカレンダー（車検予定）
- **現在の課題**:
  - 運転者が提出した紙の日報をExcelに転記する作業に1日30〜60分かかっている
  - 車検・保険の期限を自分のカレンダー登録に依存しており、登録漏れが事故（期限超過）に直結する
  - 他拠点で起きたヒヤリハットの情報が回ってこず、同じ事象が自拠点でも起きる
- **期待する解決策**: 転記作業をなくし、期限は自動で通知され、拠点横断でヒヤリ情報が見える状態
- **1日の典型的なワークフロー**:
  - 07:00 運転者の出庫対応、当日の車両割当確認
  - 10:00 前日分の日報の確認・不備の差し戻し
  - 14:00 整備工場との調整、点検予定の確認
  - 18:00 帰庫対応、日報の受領
  - 19:00 Excelへの転記、翌日の準備

### セカンダリーペルソナ: 山田直人（38歳、運転者 / 一般利用者）

- 中型トラックで日中の定期配送を担当。ITツールは業務用スマートフォンのみ
- **現在の課題**: 帰庫後に紙の日報を手書きする時間が負担。運転中に気づいた車両の異音などを報告する手段が口頭しかなく、伝わらないまま放置される
- **期待する解決策**: スマートフォンで出発・帰着と走行距離を数タップで入力でき、気づいた異常もその場で報告できること
- **1日の典型的なワークフロー**: 出庫前点検 → 出発入力 → 配送 → 給油 → 帰着入力 → 日報提出

### ターシャリーペルソナ: 鈴木美咲（33歳、本社 総務・システム管理者）

- 全拠点の車両資産と利用者アカウントを管理。経営層への報告資料を作成
- **現在の課題**: 拠点から送られるExcelのフォーマットがばらばらで、全社の車両台数・稼働状況の集計に数日かかる
- **期待する解決策**: 全拠点のデータを同一フォーマットで即座に集計・エクスポートできること
- **1日の典型的なワークフロー**: 入退社に伴うアカウント管理、車両の新規登録・廃車処理、月次の全社レポート作成

### ロールと権限

| ロール | 想定利用者 | 権限範囲 |
|--------|-----------|---------|
| 管理者 (admin) | 本社 総務・システム管理者 | 全拠点のデータ参照・編集、**ユーザー管理**、拠点マスタ管理、全社レポート |
| 運行管理者 (manager) | 営業所の運行管理者 | **所属拠点**の車両台帳・運転者台帳の管理、日報の確認・承認、点検整備記録の登録、事故・ヒヤリ報告の確認と改善報告の承認 |
| 一般利用者 (member) | 運転者 | 自分が登録した日報・事故/ヒヤリ報告の作成と参照、割当車両の情報参照、車両不具合の報告 |

## 成功指標(KPI)

測定は原則としてシステム内のデータから自動集計し、管理者ダッシュボードに表示する。ユーザビリティ関連の指標のみ、リリース後の運用ヒアリングで測定する。

### プライマリーKPI

- **運行日報の当日入力率: 95%以上（本稼働3ヶ月後）**
  - 測定方法: 「運行日（`operation_date`）当日中に提出された日報件数 ÷ 当月の提出済み日報総件数」を日次バッチで集計
- **期限超過（車検・保険・法定点検）件数: 0件（本稼働後、継続）**
  - 測定方法: 各車両の期限日と現在日を日次で突合し、期限日を過ぎて未更新の車両を計上
- **紙・Excel台帳の併用廃止: 対象5〜10拠点すべてで完了（本稼働6ヶ月後）**
  - 測定方法: 拠点ごとの車両登録率（システム登録台数 ÷ 実保有台数）が100%かつ、当月の日報提出率が95%以上である拠点を「移行完了」と判定
- **運行管理者の日報関連作業時間: 1日60分 → 15分以下（本稼働3ヶ月後）**
  - 測定方法: 本稼働前と3ヶ月後に運行管理者へ同一設問でヒアリング（対象: 全拠点の運行管理者）

### セカンダリーKPI

- **ヒヤリハット報告件数: 1拠点あたり月3件以上（本稼働6ヶ月後）**
  - 測定方法: 拠点別の月次報告件数を集計。報告しやすさの代理指標として用いる
- **改善報告の完了率: 報告済み事故・ヒヤリの80%以上が30日以内に「改善報告 承認済み」に到達（本稼働6ヶ月後）**
  - 測定方法: 報告日から承認日までの日数を集計
- **日報入力の所要時間: 1件あたり平均3分以内（本稼働3ヶ月後）**
  - 測定方法: 日報入力画面の初回表示から提出完了までの経過時間を記録し中央値を算出
- **期限アラートの事前通知リードタイム遵守: 通知対象の100%が期限60日前・30日前・7日前に通知される**
  - 測定方法: 通知ログと車両の期限日を突合

## 機能要件

### コア機能(MVP)

#### F-1. 組織・拠点・ユーザー管理

**ユーザーストーリー**:
本社のシステム管理者として、拠点ごとにデータを分離して運用するために、拠点マスタとユーザーアカウント・ロールを管理する機能が欲しい

**受け入れ条件**:
- [ ] 管理者は拠点（名称・拠点コード・住所・電話番号）を登録・編集・無効化できる
- [ ] 管理者はユーザーを登録し、氏名・メールアドレス・所属拠点・ロール（admin / manager / member）を設定できる
- [ ] ユーザーはメールアドレスとパスワードでログインできる。パスワードはハッシュ化して保存し、平文では保持しない
- [ ] manager および member は、自分の所属拠点に紐づくデータのみ一覧・詳細で参照でき、他拠点のデータにURL直接指定でアクセスした場合は 403 相当のエラー画面を表示する
- [ ] member はユーザー管理画面・拠点管理画面にアクセスできない（メニューに表示されず、直接アクセスもブロックされる）
- [ ] 管理者は退職者のアカウントを無効化でき、無効化後はログインできない（過去に登録した日報などの記録は保持される）
- [ ] 管理者はユーザーのパスワードリセット用リンクを発行できる

**優先度**: P0(必須)

#### F-2. 車両台帳管理

**ユーザーストーリー**:
運行管理者として、拠点の保有車両を正確に把握するために、車両の基本情報と法定期限を登録・管理する機能が欲しい

**受け入れ条件**:
- [ ] 管理者・運行管理者は車両を登録できる。登録項目は以下を必須とする: 車両番号（ナンバープレート）、車台番号、車種区分（大型/中型/準中型/普通/軽/その他）、メーカー、車名、初度登録年月、所属拠点、ステータス（稼働中/整備中/休車/廃車）
- [ ] 任意項目として、年式、最大積載量、車両総重量、乗車定員、燃料種別、購入/リース区分、リース満了日、任意の備考を登録できる
- [ ] 法定期限として、車検満了日・自賠責保険満了日・任意保険満了日を登録できる
- [ ] 車両番号は全社で一意であり、重複登録を試みた場合はフォーム上にエラーを表示して保存しない
- [ ] 車両一覧は拠点・ステータス・車種区分で絞り込みでき、車両番号・車名の部分一致検索ができる
- [ ] 車両詳細画面から、その車両の運行日報・点検整備記録・事故/ヒヤリ記録の履歴を参照できる
- [ ] 車両は物理削除せず、ステータスを「廃車」に変更することで一覧のデフォルト表示から除外する
- [ ] 車検証・保険証券などのファイル（PDF/JPEG/PNG、1ファイル10MBまで、1車両あたり20ファイルまで）を添付できる
- [ ] 運行管理者は自拠点の車両のみ編集でき、他拠点の車両は編集操作を行えない

**優先度**: P0(必須)

#### F-3. 運転者台帳管理

**ユーザーストーリー**:
運行管理者として、運転者の資格要件を満たした配車を行うために、運転者の免許情報を管理し、免許期限を把握する機能が欲しい

**受け入れ条件**:
- [ ] 管理者・運行管理者は運転者を登録できる。登録項目は以下を必須とする: 氏名、氏名かな、所属拠点、雇用区分（正社員/契約社員/その他）、入社年月日、免許証番号、免許種類（複数選択可）、免許証有効期限
- [ ] 運転者レコードはユーザーアカウント（F-1）と紐付けできる。紐付けられた運転者は自分の日報入力時に自動的に運転者として設定される
- [ ] 免許証有効期限が近づいた運転者は、F-5のアラート対象となる
- [ ] 運転者一覧は拠点・雇用区分で絞り込みでき、氏名・氏名かなの部分一致検索ができる
- [ ] 運転者詳細画面から、その運転者の運行日報・事故/ヒヤリ記録の履歴を参照できる
- [ ] 退職者は「退職」区分に変更することで一覧のデフォルト表示から除外する（記録は保持される）
- [ ] 運行管理者は自拠点の運転者のみ編集できる

**優先度**: P0(必須)

#### F-4. 運行日報・走行記録

**ユーザーストーリー**:
運転者として、帰庫後の手書き作業をなくすために、スマートフォンから出発・帰着と走行距離を入力して日報を提出する機能が欲しい

運行管理者として、転記作業をなくし運行実績を即座に把握するために、提出された日報を確認・承認し、車両別・運転者別に集計する機能が欲しい

**受け入れ条件**:
- [ ] 運転者は日報を新規作成できる。入力項目は以下を必須とする: 運行日、車両、運転者、出発日時、帰着日時、出発時走行距離計（オドメーター）、帰着時走行距離計
- [ ] 任意項目として、主な行き先、荷種、休憩時間（分）、備考を入力できる
- [ ] 走行距離は「帰着時オドメーター − 出発時オドメーター」でシステムが自動計算し、入力欄には表示のみ行う（手入力させない）
- [ ] 帰着時オドメーターが出発時オドメーターを下回る場合、または前回同一車両の帰着時オドメーターを下回る場合は、保存前に警告を表示する（運行管理者は理由を備考に記入して保存を続行できる）
- [ ] 帰着日時が出発日時より前の場合は保存できず、フォーム上にエラーを表示する
- [ ] 給油記録（給油日時、給油量(L)、金額、給油時オドメーター）を日報に0件以上ひも付けて登録できる
- [ ] 日報は「下書き」「提出済み」「承認済み」「差戻し」のステータスを持つ。運転者は下書き・提出、運行管理者は承認・差戻しができる
- [ ] 運行管理者が差し戻す際は差戻し理由を必須入力とし、運転者の日報一覧に差戻しとして表示される
- [ ] 日報一覧は運行日の期間、車両、運転者、ステータスで絞り込みできる
- [ ] member ロールは自分が運転者として登録された日報のみ参照・編集できる
- [ ] 提出済み・承認済みの日報は運転者自身では編集できない（差戻し後は編集可能になる）
- [ ] 車両別・運転者別・拠点別の月次走行距離と、燃費（走行距離 ÷ 給油量）を集計表示できる
- [ ] スマートフォン（画面幅375px）で、日報の新規作成から提出までを縦スクロールのみで完了できる

**優先度**: P0(必須)

#### F-5. 点検・整備記録と期限アラート

**ユーザーストーリー**:
運行管理者として、期限切れによる運行停止を防ぐために、車検・保険・法定点検の期限を自動で監視し事前に通知する機能が欲しい

**受け入れ条件**:
- [ ] 運行管理者は車両ごとに整備・点検記録を登録できる。入力項目は以下を必須とする: 実施日、種別（車検/3ヶ月点検/12ヶ月点検/日常点検/修理/オイル交換/タイヤ交換/その他）、実施時オドメーター、実施業者
- [ ] 任意項目として、費用（税込）、作業内容、次回実施予定日、請求書等の添付ファイルを登録できる
- [ ] 車検記録を登録して新しい車検満了日を入力すると、車両台帳（F-2）の車検満了日が更新される
- [ ] 以下を期限監視の対象とする: 車検満了日、自賠責保険満了日、任意保険満了日、法定点検（3ヶ月・12ヶ月）予定日、運転者の免許証有効期限
- [ ] 期限の60日前・30日前・7日前および期限当日・超過時に、対象拠点の運行管理者と管理者へメール通知を送信する
- [ ] 通知の送信結果（対象、通知日、送信可否）を記録し、管理者が一覧で確認できる
- [ ] ダッシュボードに「期限30日以内の車両」「期限超過の車両」を件数と一覧で表示する。運行管理者には自拠点分、管理者には全拠点分を表示する
- [ ] 通知メールの送信タイミングは1日1回の定時実行とし、同一対象・同一通知区分の重複送信は行わない
- [ ] 点検整備記録は車両詳細画面から時系列で参照でき、車両別の累計整備費用を集計表示できる

**優先度**: P0(必須)

#### F-6. 事故・ヒヤリ記録と改善報告

**ユーザーストーリー**:
運転者として、再発を防ぐために、運行中に経験したヒヤリハットをその場で記録・報告する機能が欲しい

運行管理者として、全社で同じ事象の再発を防ぐために、事故・ヒヤリの記録から原因分析と改善策の報告までを追跡する機能が欲しい

**受け入れ条件**:
- [ ] 運転者・運行管理者は事故/ヒヤリ記録を登録できる。入力項目は以下を必須とする: 発生日時、区分（人身事故/物損事故/車両単独/ヒヤリハット）、発生場所、車両、運転者、天候、発生状況（自由記述）
- [ ] 任意項目として、相手方の有無と概要、被害・損害の概要、警察届出の有無、現場写真（1ファイル10MBまで、1記録あたり10ファイルまで）を登録できる
- [ ] 記録は「報告済み」「原因分析中」「改善報告済み」「承認済み（完了）」のステータスを持つ
- [ ] 運行管理者は各記録に対して原因分析（直接原因・背景要因）と改善策（対策内容・実施予定日・実施責任者）を登録できる
- [ ] 管理者・運行管理者は改善報告を承認でき、承認時に承認者と承認日時を記録する
- [ ] ヒヤリハット区分の記録は、管理者が「全社共有」に設定することで、全拠点の運行管理者・運転者が参照できる（発生状況・原因・改善策のみを表示し、運転者氏名は表示しない）
- [ ] 全社共有されていない記録は、発生拠点のユーザーのみ参照できる
- [ ] 事故/ヒヤリ一覧は発生日の期間、区分、ステータス、拠点、車両で絞り込みできる
- [ ] 拠点別・区分別・月別の発生件数を集計表示できる
- [ ] 運転者は、車両の不具合（異音・警告灯点灯など）を車両単独区分として報告でき、報告は当該車両の運行管理者のダッシュボードに未対応として表示される

**優先度**: P0(必須)

#### F-7. ダッシュボードとデータ出力

**ユーザーストーリー**:
運行管理者として、朝一番に当日対応すべきことを把握するために、未処理タスクと警告をまとめて表示するダッシュボードが欲しい

本社の管理者として、経営層への報告資料を作成するために、集計データをCSVで出力する機能が欲しい

**受け入れ条件**:
- [ ] ログイン後の最初の画面としてダッシュボードを表示する
- [ ] 運行管理者のダッシュボードには、自拠点の以下を表示する: 期限30日以内/超過の車両件数、未承認の日報件数、未対応の車両不具合報告件数、改善報告が未完了の事故/ヒヤリ件数、当月の稼働車両台数
- [ ] 管理者のダッシュボードには、上記を全拠点横断および拠点別に表示する
- [ ] 運転者のダッシュボードには、自分の未提出/差戻しの日報と、割当車両の情報を表示する
- [ ] 各カウントはクリックで該当する絞り込み済み一覧画面に遷移する
- [ ] 管理者・運行管理者は、車両一覧・運転者一覧・運行日報・点検整備記録・事故/ヒヤリ記録を、画面上の絞り込み条件を反映したCSVとして出力できる
- [ ] CSVの文字コードは UTF-8 (BOM付き) とし、Excelで開いた際に文字化けしない

**優先度**: P1(重要)

### 将来的な機能(Post-MVP)

#### F-8. 点呼記録・アルコールチェック記録

乗務前後の点呼実施記録（点呼方法、実施者、健康状態確認、アルコール検知器の測定値）を登録し、法定の1年保存に対応する。検知器との連携やクラウド点呼への対応も検討する。

**優先度**: P1(重要) ※本稼働後の最優先追加機能

#### F-9. 拘束時間・休息期間の管理

改善基準告示に基づく運転者の拘束時間・休息期間・連続運転時間を日報データから自動算出し、基準超過の警告を運行管理者に表示する。

**優先度**: P1(重要)

#### F-10. 車両の予約・配車管理

車両の予約申請と承認、カレンダー形式での空き状況表示、重複予約の防止。日次の配車計画作成を支援する。

**優先度**: P2(できれば)

#### F-11. デジタコ・GPSデータ連携

デジタルタコグラフやGPS端末から走行距離・運行時間を自動取り込みし、日報の手入力項目をさらに削減する。

**優先度**: P2(できれば)

#### F-12. 燃費・コスト分析レポート

車両別・車種別の燃費推移、走行距離あたりコスト（燃料費＋整備費）の可視化、車両更新時期の判断支援。

**優先度**: P2(できれば)

#### F-13. モバイルプッシュ通知

期限アラートや日報差戻しを、メールに加えてプッシュ通知で届ける（PWA化を含む）。

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス

想定データ規模: 車両300台、運転者300名、ユーザー300アカウント、拠点10、運行日報 年間約75,000件（300台 × 250稼働日）、5年運用で約375,000件

- 各一覧画面の初回表示: 1.0秒以内（P95、1ページ50件表示、日報テーブル50万件時点）
- ダッシュボードの表示完了: 2.0秒以内（P95）
- 日報の保存操作（提出）: 500ms以内（P95）
- 検索・絞り込みの再描画: 500ms以内（P95）
- CSV出力: 10,000件を10秒以内に生成
- 同時接続ユーザー数: 100セッションで上記の応答時間を維持する
- 一覧はすべてページネーションを行い、全件をメモリに読み込まない

### ユーザビリティ

- 運転者が初回ログインから日報1件の提出を完了するまで、口頭説明のみ（マニュアル参照なし）で5分以内に到達できる（本稼働前のユーザビリティテストで運転者5名を対象に測定）
- 日報入力は、画面幅375pxのスマートフォンで横スクロールなしに完了できる
- 日報1件あたりの入力所要時間の中央値が3分以内（KPIと同一の測定方法）
- 入力エラーは該当フィールドの直下に日本語で表示し、何を修正すべきかが読み取れる文言とする
- 主要な画面（ダッシュボード、車両一覧、日報一覧）へはトップナビゲーションから2クリック以内で到達できる
- 対応ブラウザ: Chrome / Edge / Safari の最新2バージョン、iOS Safari / Android Chrome の最新2バージョン
- 表示言語は日本語のみ。日付は `YYYY/MM/DD`、日時は `YYYY/MM/DD HH:MM` 形式で統一する

### 信頼性

- 稼働率: 平日 05:00〜23:00（JST）において99.5%以上（月間の許容停止時間 約2.3時間）
- データベースは1日1回の自動バックアップを取得し、7世代を保持する。復旧手順を文書化し、年1回リストア訓練を行う
- 入力中のデータ損失を防ぐため、日報の下書き保存を提供する
- 期限アラートの定時実行が失敗した場合はエラーログを記録し、管理者へ通知する。翌実行時に未送信分を送信する
- 複数レコードの更新を伴う操作（日報＋給油記録の同時保存など）はトランザクションで実行し、部分的な保存状態を発生させない

### セキュリティ

- パスワードは Argon2 または bcrypt でハッシュ化して保存する。平文・可逆暗号での保存は行わない
- パスワードポリシー: 12文字以上、ログイン失敗10回で15分間のアカウントロック
- セッションの有効期限は最終操作から8時間とし、以降は再ログインを求める
- 認可は「ルーター（live_session）」「LiveView/コントローラ」「クエリ（拠点スコープ）」の3層で実施し、いずれか1層の漏れで他拠点データが露出しない設計とする
- 台帳の作成・更新・削除、ユーザー権限の変更、日報の承認・差戻し、事故記録の全社共有設定について、操作者・操作日時・対象・変更内容を監査ログに記録する。監査ログは管理者のみ参照でき、改変・削除はできない
- 添付ファイルは拡張子とMIMEタイプを検証し、許可された形式（PDF / JPEG / PNG）以外を受け付けない
- 通信は全経路HTTPS。HSTSを有効にする
- 秘密情報（DB接続情報、メール送信設定）は環境変数経由で `runtime.exs` に集約し、リポジトリにコミットしない
- 個人情報（運転者の氏名・免許証番号・事故記録）を含む画面では、ブラウザキャッシュを無効化する

### データ保持

- 運行日報・給油記録: 5年間保持（法定の1年保存を上回る運用要件）
- 点検整備記録: 車両の廃車後も5年間保持
- 事故・ヒヤリ記録: 10年間保持
- 監査ログ: 3年間保持
- 退職者・廃車の記録は論理削除とし、物理削除は行わない

### スケーラビリティ

- 車両1,000台・ユーザー1,000アカウント・日報200万件まで、DBインデックスの追加のみで上記パフォーマンス要件を維持できるデータモデルとする
- 拠点数の増加はマスタデータの追加のみで対応でき、コード変更を必要としない
- アプリケーションサーバーは水平スケール可能な構成とし、セッションやアップロードファイルをローカルディスクに依存させない

## スコープ外

本フェーズで明示的にスコープ外とする項目:

- **マルチテナントSaaSとしての提供**（自社向け単一テナントに限定。テナント分離・契約プラン・課金は実装しない）
- **点呼記録・アルコールチェック記録**（F-8としてPost-MVPで対応）
- **拘束時間・休息期間の法令チェック**（F-9としてPost-MVPで対応）
- **車両の予約・配車計画機能**（F-10としてPost-MVPで対応）
- **デジタコ・GPS・車載器とのリアルタイム連携**（F-11としてPost-MVPで対応）
- **会計システム・給与システムとの連携**（燃料費・整備費の会計仕訳連携は行わない。CSV出力までを提供する）
- **荷主向けの外部公開機能**（配送状況の外部への公開、顧客ポータル）
- **ネイティブモバイルアプリ**（レスポンシブWebで対応。PWA化はF-13として将来検討）
- **オフライン入力**（通信圏外での日報入力とその後の同期）
- **日本語以外の多言語対応**
- **運転者の勤怠・給与計算**（人事システムの領域）
- **配送伝票・請求書の発行**
