# 批判的分析スキル

このスキルは、`docs/ideas/` 配下の設計ドキュメントをコードベースの実態と照合し、実装前に問題を発見するためのものです。

## 実行フロー

### 1. 対象ドキュメントの特定

引数でファイルパスが指定された場合はそれを使用する。指定がない場合は `docs/ideas/` 配下のファイル一覧を表示してユーザーに選択を求める。

```bash
ls docs/ideas/
```

### 2. コードベースの調査（並列実行）

以下を Agent（Explore）で並列調査する:

**Agent 1: データ層の調査**
- 対象ドキュメントが言及するテーブルに対応する既存スキーマ・マイグレーションを調査
- 既存の類似テーブル設計（カラム名・型・制約・インデックス）を確認
- `priv/repo/migrations/` の全マイグレーション一覧を確認

**Agent 2: ビジネスロジック層の調査**
- 対象ドキュメントが言及するコンテキスト・スキーマの既存実装を調査
- 類似機能の実装パターン（クエリ設計・バリデーション・トランザクション）を確認

**Agent 3: フロントエンド・ドメイン層の調査**
- `docs/glossary.md`・`docs/functional-design.md` の関連定義を確認
- 対象機能に関連する LiveView・ルーティングの既存実装を確認

### 3. 批判的分析の観点

以下の9つの観点で文書を評価する:

#### 3-1. DB設計の妥当性
- 専用テーブルが本当に必要か（既存テーブルへのカラム追加で済まないか）
- 冗長カラム（「常にX」と注釈が必要なカラムは設計の誤りサイン）
- 非正規化（カンマ区切り文字列・JSON保存など）がないか
- 既存テーブルの設計思想（スナップショット・論理削除・ULID等）と一致しているか

#### 3-2. 既存実装との整合性
- 類似機能の既存実装パターンと設計が矛盾していないか
- 参照経路（FK連鎖）が既存パターンと揃っているか
- 命名規則（テーブル名・カラム名・モジュール名）が統一されているか

#### 3-3. ビジネスルールの正確性
- ステータス判定ロジックが `glossary.md`・`functional-design.md` の定義と一致しているか
- 複数レコードが存在する場合の「最新」判定が正確か
- 複数エンティティが絡む場合の条件が曖昧でないか

#### 3-4. 制約の網羅性
- ユニーク制約が必要な箇所に定義されているか
- 既存の類似機能で設けられている制約が漏れていないか

#### 3-5. 運用フローの完全性
- 承認フロー・キャンセルフロー・修正フローが定義されているか
- 「承認不要」と「訂正不要」を混同していないか
- 誤操作時のリカバリ手段が存在するか

#### 3-6. 用語・ドメイン定義の整合性
- `glossary.md` に新規用語が定義されているか
- `CLAUDE.md` のスペック駆動開発プロセスに従っているか（`ideas/` から直接実装に進もうとしていないか）

#### 3-7. フィールド・型の曖昧さ
- 同義・類似フィールドが既存テーブルに存在する場合、どちらを使うか明記されているか
- 型の選択（`string` vs FK参照、`naive_datetime` vs `date` 等）に根拠があるか

#### 3-8. 命名の一貫性
- カラム名・URL・モジュール名が既存の命名規則と揃っているか
- 既存の類似カラムと同じ名前を別の意味で使っていないか

#### 3-9. 実装方針の未定義事項
- PDF生成・通知・外部サービス連携など、実装上の重要事項が抜けていないか
- 既存の同種実装（フック・コンポーネント等）の流用可否が検討されているか

### 4. レポートの生成

分析結果を以下のフォーマットで `docs/ideas/` に出力する。

**出力ファイル名:** 対象ファイル名の末尾に `-critical-review` を付与
- 例: `prime-contractor-and-admin-invoice.md` → `prime-contractor-and-admin-invoice-critical-review.md`

**レポートフォーマット:**

```markdown
# 批判的分析レポート: `{対象ファイル名}` の全否定

作成日: {YYYY-MM-DD}
対象文書: `{対象ファイルパス}`

---

## 総評

{文書の現状評価: 実装に進めるべき状態か否かを1〜3文で結論から述べる}

---

## {番号}. {問題のタイトル}

**問題:** {何が問題か}

**証拠:** {コードベース上の根拠: ファイルパス・行番号・既存実装の内容}

**批判:** {なぜこれが問題なのか、どうすべきか}

---

（問題ごとに繰り返す）

---

## まとめ：実装着手の前提条件

| # | 必要作業 |
|---|--------|
| 1 | {必要な修正・定義・設計変更} |
...
```

### 5. 出力後の確認

レポートを出力したら、ファイルパスをユーザーに伝え、承認を求める。

## 重要なルール

- **コードベースの実態を根拠にする**: 「一般論として悪い」ではなく「このプロジェクトの `lib/xxx.ex:NN` がこうなっているから矛盾する」という形で指摘する
- **`glossary.md` と `functional-design.md` を権威として扱う**: ドメイン定義はこれらに従う
- **問題がない項目は指摘しない**: 問題のある箇所のみを列挙する（無理に9項目埋めない）
- **1ファイルずつ処理する**: 複数ファイルを一度に処理しない
