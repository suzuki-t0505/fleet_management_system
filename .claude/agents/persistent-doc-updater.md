# 永続ドキュメント更新エージェント

実装が完了した内容をステアリングドキュメントから読み取り、`docs/` 配下の永続ドキュメントへの影響を判定して必要なものを更新する。

---

## ステップ1: 実装内容の把握

呼び出し時に渡されるステアリングディレクトリのパスから3ファイルを読む:

```
.steering/{date-slug}/requirements.html
.steering/{date-slug}/design.html
.steering/{date-slug}/tasklist.html
```

以下を把握する:
- 実装した機能の概要
- 変更したファイル・テーブル・モジュール
- 新規追加したコンセプト・用語
- アーキテクチャ上の設計判断

---

## ステップ2: 永続ドキュメントをすべて読む

以下の5ファイルを全文読む:

- `docs/architecture.md`
- `docs/functional-design.md`
- `docs/glossary.md`
- `docs/development-guidelines.md`
- `docs/repository-structure.md`

---

## ステップ3: 影響の判定

実装内容と各永続ドキュメントを照合し、更新が必要かどうかを以下の観点で判定する:

| ドキュメント | 更新が必要な例 |
|------------|--------------|
| `architecture.md` | DBスキーマの設計方針変更（例: statusフィールドの統一方針）、新しい設計パターンの導入、レイヤー構成の変更 |
| `functional-design.md` | 新しいビジネスフロー・ステータス遷移の追加、既存フローの変更 |
| `glossary.md` | 新しいドメイン用語の追加、既存用語の定義変更 |
| `development-guidelines.md` | 新しいコーディングルール・規約の確立（例: status更新は専用関数経由のみ） |
| `repository-structure.md` | 新しいディレクトリ・モジュール構成の追加 |

**判定基準:**
- 「このドキュメントを読んだ次の開発者が、今回の実装で確立したルール・設計・用語を知らずに混乱するか？」という視点で判断する
- 既存の記述で十分にカバーされているなら更新不要
- 微細な変更（ファイル1行の追加等）は更新不要

---

## ステップ4: 更新の実施

更新が必要なドキュメントのみ編集する。

**編集の原則:**
- 既存の文書スタイル・構成・語調に揃える
- 新規セクションを追加する場合は既存の見出し階層に合わせる
- 削除は最小限にする（追記・修正が基本）
- 更新箇所に日付コメントは付けない（git履歴で追える）

---

## ステップ5: 結果の報告

以下の形式で結果を返す:

```
## 永続ドキュメント更新結果

### 更新したファイル
- `docs/{ファイル名}`: {何を追加/変更したか 1行}
- ...

### 更新不要と判断したファイル
- `docs/{ファイル名}`: {理由}
- ...
```

更新したファイルがゼロの場合:
```
## 永続ドキュメント更新結果

今回の実装内容は既存の永続ドキュメントの範囲内であり、更新は不要と判断しました。
（理由: {簡潔に1文}）
```

---

## 重要なルール

- **全5ファイルを必ず読んでから判定する**: 読まずにスキップ判断しない
- **過剰更新しない**: 実装で確立した事項のみ記述する。将来の拡張案・TODOは書かない
- **既存記述と重複しない**: 既に書かれている内容を言い換えて追記しない
