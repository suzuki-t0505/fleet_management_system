設計：MCPによる配車表の取り込み

requirements ／ design ／ tasklist

構成

ファイル役割
CoreAppWeb.McpControllerJSON-RPC（initialize / ping / tools/list / tools/call）。通知は202、GET・DELETEは405
CoreAppWeb.Plugs.McpAuthBearerトークン→Scope。無効は401
CoreAppWeb.Mcp.Tools / Tools.Masters / Tools.Dispatchesツールの定義と実行。Contextの公開APIだけを呼ぶ
CoreApp.Dispatches.Import名称→マスタIDの解決、入力値の組み立て、エラー整形（純関数）
CoreApp.Dispatchesvalidate_import/2・import_dispatches/3（既存の change_dispatch/3・create_dispatch/3 を再利用）
Accounts / UserTokenMCPトークン（context "mcp"、ハッシュ保存、90日、有効な利用者のみ）
mix core_app.mcp.gen_tokenトークン発行

トークン管理画面

  • ApiTokenLive.Manager.Index（/management/api_tokens、:require_manager）。自分のトークンだけを扱う
  • Accounts.list_mcp_tokens/1 / create_mcp_token/2 / revoke_mcp_token/3。発行・失効は監査ログ（api_token）と同一トランザクション。トークンの値は変更内容に含めない
  • 平文は発行時のアサイン（new_token）にだけ持ち、閉じる・再読み込みで消える。一覧はハッシュしか無いため発行日時と有効期限だけを表示する
  • コピーは phx:copy（app.js）。Claude Code への登録コマンドを平文入りで表示する
  • スキーマ変更なし（名前・最終利用日時は将来の拡張）

判断

  • MCPライブラリを使わず自前の stateless 実装にした。当初は anubis_mcp を第一候補としたが、リクエストごとに認証して Scope を作る必要があり、セッション状態を持つ実装と相性が悪い。必要なメソッドは4つだけで依存を増やすほどではない（Elixir 1.20 との互換確認も不要になる）
  • 表の解析はクライアント側。列構成を固定せず、xlsx 解析の依存を持たない
  • ドメインの層は Context + スキーマの2層のまま（coding-rules 2.1）。Import は Dispatches.Board と同じ純関数のモジュールで、Repo を触る処理は Dispatches に置く
  • ドライバー・荷主は車両の拠点のものから探す。管理者で他拠点に同名がある場合の曖昧さを避け、V-33・V-34 とも整合する
  • 二重登録の判定キーは「車両・ドライバー・開始日時・タイトル」。再取り込みで止まる一方、同じ時間帯の別便（タイトル違い）は警告にとどまる
  • 全行有効のときだけ1トランザクションで登録する。途中の行で失敗したらロールバックし、失敗行にエラーを付けて返す

ツール

名前内容
list_vehicles / list_drivers / list_shippers配車に選べるマスタの一覧。q で表記ゆれを無視した部分一致
validate_dispatches保存せず検証。行ごとに status / errors / warnings / summary
create_dispatches全行有効なら登録。エラーがあれば何も登録せず結果を返す
list_dispatches期間・検索ワード等で配車を参照

セキュリティ

  • DBにはトークンのSHA-256ハッシュのみ保存。セッショントークンは流用できない（contextが違う）
  • 無効化された利用者・期限切れ・不正な値は401
  • 権限判定は各Contextの Scope で行う。他拠点のマスタは名称が同じでも解決しない
  • トークンはリポジトリにコミットしない（README は環境変数で渡す）
