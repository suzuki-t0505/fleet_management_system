設計：事故・ヒヤリ記録と改善報告

requirements.html の要求を実装に落とす。 規範は coding-rules.md と DESIGN-notion.md。

1. 全体構成

集約を2つ追加する。事故・ヒヤリ（incidents）と、汎用の添付ファイル（attachments）。 添付は車両・点検整備からも使えるよう、対象を限定しないポリモーフィックな集約にする。

    ├── storage/local.ex    # 開発・テスト用。ローカルディスクに保存
    └── storage/gcs.ex      # 本番用。goth + google_api_storage

2. データベース

いずれも functional-design 4.3 の定義どおり。

インデックス目的
incidents (office_id, occurred_at)一覧の既定並び（拠点スコープ + 発生日時降順）
incidents (vehicle_id, occurred_at)車両ごとの履歴
incidents (status, office_id)未対応・未完了の件数（ダッシュボード）
incidents (shared_company_wide)全社共有された記録の横断参照
attachments (attachable_type, attachable_id)対象に紐づく添付の取得

attachments は対象が3種類（車両・点検整備・事故）あるため外部キー制約を張らない （alert_notifications と同じ扱い）。

3. 事故・ヒヤリ

3.1 参照できる範囲

ロール見える記録
admin全件
manager自拠点の全件 ＋ 他拠点の全社共有された記録
member自分が報告した記録 ＋ 自分が運転者の記録 ＋ 全社共有された記録
設計判断 D-1：member の範囲に「自分が運転者の記録」を含める
functional-design 3.2 の画面一覧は「自分の報告＋全社共有」と書いているが、2.1 のデータスコープは 「自分が作成した記録・自分が運転者の記録」である。当事者が自分の事故記録を読めないのは不自然なため、 広い方（2.1）に合わせる。functional-design 3.2 の表記を実装に合わせて更新する。

3.2 状態遷移

運行日報と同じく、業務上の動詞を Context 関数にする。

start_analysis(scope, incident, opts)          # reported → analyzing（運行管理者）
report_countermeasure(scope, incident, attrs)  # analyzing → countermeasure_reported（V-25）
approve_incident(scope, incident, opts)        # countermeasure_reported → closed（V-26）
reject_incident(scope, incident, opts)         # countermeasure_reported → analyzing
share_incident(scope, incident, shared?, opts) # 全社共有の設定（管理者のみ）

いずれも監査ログを同一トランザクションで記録する（承認は approve、差戻しは reject、 共有設定は share）。

設計判断 D-2：差戻しの理由欄は作らない
incidents には rejected_reason に相当するカラムが無い（日報とは異なる）。 カラムを増やすより、差戻しは「分析中に戻す」操作と割り切り、理由は改善策の欄で伝える運用にする。 差し戻した事実は監査ログに残る。

3.3 編集できる範囲

ロール編集できる記録
admin完了（closed）以外のすべて
manager自拠点の、完了以外
member自分が報告した、報告直後（reported）のみ

原因分析・改善策の入力は運行管理者以上のみ。一般利用者のフォームには表示しない。

3.4 匿名化（V-27）

「全社共有された記録を他拠点の利用者が見る場合」に運転者氏名・報告者氏名を伏せる。 判定は Context に置き（Incidents.anonymize?/2）、Web 層は真偽だけを見て表示を切り替える。 管理者は全拠点の責任者のため対象外とする。

4. 添付ファイル

4.1 ストレージの抽象化

defmodule CoreApp.Utils.Storage do
  @callback put(key :: String.t(), path :: String.t(), content_type :: String.t()) ::
              :ok | {:error, term()}
  @callback read(key :: String.t()) :: {:ok, binary()} | {:error, term()}
  @callback url(key :: String.t()) :: {:ok, String.t()} | :stream
  @callback delete(key :: String.t()) :: :ok | {:error, term()}
end

アダプタは config :core_app, :storage, adapter: ... で差し替える。 coding-rules 13.3 に従い、モジュール属性ではなく関数で解決する。

環境アダプタダウンロード
dev / testStorage.Local（priv/uploads 配下）:stream（アプリが配信）
prodStorage.Gcs15分の署名付きURLへ転送
設計判断 D-3：ダウンロードは必ずアプリのコントローラを通す
署名付きURLでも、URLを知っていれば誰でも読めてしまう。AttachmentController で 対象レコードをスコープ付きで引き直してから配信・転送する。参照できない利用者は 404 相当で弾く。 公開URLはデータベースにもHTMLにも持たせない。
設計判断 D-4：GCS アダプタは未検証で入る
開発環境にサービスアカウントの認証情報が無いため、実行経路を確認できない。 テストはローカルアダプタに対して書き、GCS アダプタは本番設定時に疎通確認する前提とする。 この状態を README とドキュメントに明記する。

4.2 検証（V-28）

項目扱い
形式PDF / JPEG / PNG。allow_upload の accept に加え、先頭バイト（マジックナンバー）を検証する
サイズ1ファイル10MB。max_file_size で弾く
件数1記録10ファイル。既存の添付数を数えてから上限を決める（max_entries だけでは通算を守れない）
保存先キーattachments/{attachable_type}/{attachable_id}/{ULID}_{元ファイル名}（architecture 4.4）

削除は行レコードだけを消し、実体は消さない（architecture 4.4 の方針。ローカルアダプタも同じ挙動にそろえる）。

5. 画面

URL内容
/incidents一覧。自分の報告・自分が運転者・全社共有。区分とステータスで絞り込み
/incidents/new・/incidents/:id/edit報告フォーム（1カラム）。発生状況と写真の添付まで375pxで完了できる
/incidents/:id詳細。進捗と改善策を参照。他拠点の共有記録は氏名を伏せる
/management/incidents一覧。区分・ステータス・期間・拠点・全社共有で絞り込み。発生日時の降順
/management/incidents/:id詳細・分析・承認。状態に応じて操作ボタンを出し分ける。報告者本人には承認ボタンを出さない
/attachments/:id添付のダウンロード（コントローラ）

ステータスバッジは既存の <.status_badge> に :incident 種別を足す。 車両詳細に事故・ヒヤリ履歴（直近5件）を追加し、ダッシュボードのプレースホルダを実際の件数に差し替える。
