設計：プロジェクト初期整備

要求内容は requirements.html を参照。本書は「どう実装するか」を定義する。

1. 全体方針

  • 業務機能を作らない。土台（依存・認証・レイアウト・デザイントークン）のみを用意する
  • 拠点（offices）だけは例外的に作る。users.office_id の外部キーに必要なため、テーブルと最小の Context を用意し、管理画面は作らない
  • 各ステップの後に make check を実行し、常に緑の状態を保ちながら進める
  • ジェネレータの生成物は、coding-rules.md に反する部分のみ手直しする。過剰な書き換えをしない

2. 依存の追加（R-1 / R-2）

ライブラリバージョン用途・設定
credo~> 1.7only: [:dev, :test], runtime: false。mix credo.gen.config で .credo.exs を生成し、既定のまま開始する

nimble_csv~> 1.2依存追加のみ
方針：goth / google_api_storage / nimble_csv は「使う時になって依存追加でビルドが壊れる」ことを避けるため先に入れる。ただし起動プロセスには組み込まない（goth を supervision tree に入れるのは GCP の認証情報が用意できてから）。

4. 認証基盤（R-4）

4.1 生成

docker compose run --rm web mix phx.gen.auth Accounts User users

生成後に mix deps.get と mix ecto.migrate を実行する。

Phoenix 1.8 の phx.gen.auth は既定でマジックリンクログインを含む。本システムは管理者がアカウントを発行し、パスワードでログインする方針（architecture.md 4.1）のため、生成後に以下を行う。
  • サインアップ（/users/register）のルートを削除する
  • マジックリンク関連の画面・ルートの扱いは、生成物を確認してから判断する（初回パスワード設定リンクに転用できる場合は残す）

4.2 users テーブルへの追加カラム

カラム型用途
office_idULID / FK所属拠点。NOT NULL
namestring(100)氏名。NOT NULL
rolestringadmin / manager / member。NOT NULL, default member
activeboolean無効化フラグ。NOT NULL, default true
failed_attemptsintegerログイン失敗回数。NOT NULL, default 0
locked_untilutc_datetimeロック解除日時

生成された users のマイグレーションを直接編集せず、別マイグレーション（add_office_and_role_to_users）で追加する。主キーは Ecto.ULID に統一する。

4.3 Accounts.Scope の拡張

# lib/core_app/accounts/scope.ex
defstruct user: nil, office_id: nil, role: nil, driver_id: nil

def for_user(%User{} = user) do
  %__MODULE__{
    user: user,
    office_id: user.office_id,
    role: String.to_existing_atom(user.role),
    driver_id: nil          # drivers 実装時に紐付ける
  }
end

def admin?(%__MODULE__{role: :admin}), do: true
def admin?(_), do: false

def manager?(%__MODULE__{role: role}), do: role in [:admin, :manager]
この段階では driver_id は常に nil。drivers テーブルを作る作業で for_user/1 に紐付けを追加する。

4.4 認可フックとルーター

coding-rules.md 8.3 に従い、pipeline の plug と on_mount の強さを一致させる。

live_sessionon_mount対象URL
:require_authenticated_user{UserAuth, :ensure_authenticated}/, /operation_reports, /incidents, /vehicles
:require_manager{UserAuth, :ensure_manager}/management/*（台帳・日報・点検・事故・集計）
:require_admin{UserAuth, :ensure_admin}/management/users, /management/offices, /management/audit_logs, /management/live_dashboard

本作業では3つの live_session の枠とフックのみを用意し、配下のルートはダッシュボードだけを登録する。各画面は機能実装時に追加する。

ensure_manager / ensure_admin は、権限不足時に 403 相当のフラッシュを出して / に halt する。

4.5 アカウントロック

ログイン失敗時に failed_attempts を加算し、10回で locked_until = now + 15分 を設定する。成功時は 0 にリセットする。ロック中は認証情報が正しくてもログインさせない。

5. 拠点の最小実装（R-4 の前提）

offices テーブルと CoreApp.Offices Context を作る。定義は functional-design.md 4.3 のとおり（code / name / postal_code / address / phone / active）。

本作業で用意する関数は list_offices/0 と get_office!/1 のみ。管理画面（/management/offices）は作らない。

この Context は全拠点を横断して参照する性質のため、scope を取らない例外とする（development-guidelines.md 6.1）。拠点の一覧はロールに関わらず選択肢として必要になるため。

10. 実装順序

各ステップの完了時に make check を実行する。

  1. 既存ファイルの修正（R-7〜R-10）— 影響が小さく、以降の作業の足場になる
  2. credo 導入（R-1）— ここで品質ゲートが有効になる
  3. 依存追加（R-2）— ビルドが通ることだけを確認
  4. 拠点テーブル（5章）— 認証の前提
  5. 認証基盤（R-4）— 生成 → カラム追加 → Scope 拡張 → ルーター整理 → ロック実装
  6. Oban（R-3）— 認証と独立。マイグレーション → 設定 → 起動
  7. デザイントークン（R-5）
  8. Layouts.app + ダッシュボードの枠（R-6）
  9. seeds → 通しで動作確認（C-1〜C-7）

11. テスト方針

対象テスト内容
Accounts.Scopeロールごとに admin?/1 manager?/1 が期待どおりを返す
アカウントロック10回失敗でロックされ、ロック中は正しいパスワードでもログインできない。成功時にカウントがリセットされる
UserAuth の on_mountmember が :ensure_manager の live_session にアクセスするとリダイレクトされる
無効化ユーザーactive = false のユーザーはログインできない
Officeslist_offices/0 が active の拠点のみを返す
レイアウトロールごとにナビゲーション項目の出し分けが正しい

phx.gen.auth が生成するテストは削除せず維持する。サインアップを削除した場合は、対応するテストのみ削除する。

12. リスクと対応

リスク対応
Phoenix 1.8 の phx.gen.auth の生成物が想定と異なる（マジックリンク前提の構成）生成直後に内容を確認し、方針との差分を報告してから手直しする。差分が大きい場合は設計を更新する
ULID（Ecto.ULID）とジェネレータの binary_id 設定の噛み合わせ生成されたマイグレーション・スキーマの主キー型を Ecto.ULID に揃えてから ecto.migrate する
Tailwind v4 の @utility 記法がバージョンで異なるビルドが通らない場合は @layer components での定義に切り替える。トークン値自体は変えない
credo 導入で既存コードに大量の指摘が出る既定設定で開始し、テンプレート由来の指摘は .credo.exs で除外せず修正する。修正が広範に及ぶ場合のみ報告して判断を仰ぐ
make check が Docker 未起動で失敗する実行前に make up の状態を確認する
