2. 集計（Reports）

レポート軸指標
走行距離月 × 車両 / 運転者 / 拠点走行距離合計、稼働日数（日報の件数ではなく運行日の異なり数）
燃費月 × 車両走行距離 ÷ 給油量、給油量合計、給油金額合計
整備費月 × 車両 / 拠点費用合計、件数、区分別の内訳
事故・ヒヤリ月 × 拠点 × 区分発生件数、改善報告の完了率（closed ÷ 全件）

集計対象は status = approved の日報のみ（functional-design 8.2）。 月は JSTの運行日・実施日・発生日で切る。occurred_at のような日時は (occurred_at + 9 hours) で日付に直してから月を取る。

設計判断 D-1：集計結果も subquery で包んでページネーションする
group_by したクエリをそのまま数えると「グループごとの件数」が返り、行数にならない。 期限アラートと同じく from r in subquery(grouped) で包み、既存の Pagination を通す。

2.1 期間の指定

from / to を月単位（YYYY-MM）で受け取る。既定は直近6ヶ月。 拠点の絞り込みは管理者のみ有効で、運行管理者は自拠点に固定する（他のContextと同じ）。

3. CSV出力（Exports）

設計判断 D-2：非同期生成をやめ、ストリーミング配信にする
architecture.md 4.7 は「10,000件超は CsvExportWorker で非同期生成 → GCS → 完了メールに署名URL」だったが、 チャンク転送（Plug.Conn.chunk/2）＋ Repo.stream/2 にすれば、 50,000件でも全件をメモリに載せずにその場で返せる。
ワーカー・GCS・署名URL・完了メールがすべて不要になり、 「添付のダウンロードはアプリを経由する（署名URLを発行しない）」という F-6 の方針とも揃う。 architecture.md 4.7 を更新する。 
# Exports の公開API
count(scope, resource, params)             # 上限判定に使う
stream_rows(scope, resource, params, fun)  # トランザクション内で行ストリームを fun に渡す
headers(resource)                          # 日本語のヘッダー行

対象は vehicles / drivers / operation_reports / maintenances / incidents の5種。集計レポートのCSVは行数が小さいため、表示中の集計結果をそのまま書き出す。

設計判断 D-3：Exports は専用のクエリを持つ
CSVは平坦な列が要るため、一覧の preload とは形が違う（Repo.stream は preload を実行できない）。 各Contextの private な絞り込み関数を公開する代わりに、Exports に join + select のクエリを置く。 絞り込みの条件は一覧と同じ意味になるよう、同じパラメータ名を受け取る。

3.1 形式（9.2）

項目実装
文字コードUTF-8。先頭に BOM（﻿）を出す
改行CRLF。NimbleCSV.define(..., escape: "\\"", line_separator: "\\r\\n")
ヘッダー日本語の項目名（列挙値も日本語に変換して出す）
上限50,000件。超過時は出力せず、一覧へ戻してメッセージを出す
ファイル名{resource}_{YYYYMMDD}.csv。RFC 5987 で指定する

3.2 認可

ルーターは /management/exports/... に置き、require_manager_user plug を通す。 スコープは各クエリに必ず付与するため、運行管理者のCSVに他拠点の行は入らない。

4. ダッシュボード

ロール追加する表示
member直近7日の自分の日報一覧、直近に運転した車両
manager当月の稼働車両台数（運行実績のある車両の異なり数）、当月の総走行距離
admin拠点別の内訳表（期限超過・未承認日報・未完了の改善報告・当月の走行距離）

「割当車両」はデータモデルに無いため、直近の日報の車両で代替する（requirements 4章）。
