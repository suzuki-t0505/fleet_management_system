.steering / 20260913-driver-registry

設計：運転者台帳

要求内容は requirements.html。

1. 全体方針

  • 車両台帳の構成をそのまま踏襲する。Context のシグネチャ（scope 第1引数）、監査ログの記録方法、画面構成、共通コンポーネントの使い方を変えない
  • 2つ目の台帳として、共通化の要否を判断する。同じコードが3回目に現れたら抽象化する方針とし、今回は「重複しているが抽象化しない」判断も記録に残す
  • users と drivers の紐付けは drivers.user_id 側に持つ（1運転者に1アカウント。アカウントを持たない運転者が存在するため）

2. データモデル

要求内容との差異：requirements.html では運転者コードを「任意項目」と書いたが、 functional-design.md 4.3 では code は NOT NULL かつ全社ユニークである。 上位ドキュメントを正とし、必須項目とする（repository-structure.md 11章）。 採番規則は運用側の既存規則に合わせる必要があるため、システムでの自動採番は行わない。

2.2 免許種類

{:array, Ecto.Enum} で保持する。運送事業で使う区分に限定する。

large(大型) / medium(中型) / semi_medium(準中型) / ordinary(普通) /
large_special(大型特殊) / towing(けん引)

2.3 users との関連

# lib/core_app/accounts/user.ex

Context をまたぐスキーマ参照になるが、Ecto の関連定義としては通常の書き方であり、 Accounts が Drivers の Context 関数を呼ぶわけではないため許容する。

Scope.for_user/1 はテストやログイン処理など preload していない User でも呼ばれるため、 Ecto.Association.NotLoaded を nil として扱う。 日報（F-4）で確実に値が必要になる箇所では、preload 済みの経路（セッション）から取得する。

  • セクション：基本情報 / 免許情報 / アカウント / 備考

6. 共通化の判断

車両台帳と重複する要素について、今回の対応を明記する。

重複箇所今回の対応理由
スコープ適用（scoped/2）各 Context に複製3行の私的関数。共通化するとクエリの起点が隠れ、追いにくくなる
監査ログ付きCRUD（Multi）各 Context に複製リソース種別と changeset の組み立てが異なる。3つ目の台帳で共通化を再検討する
一覧の絞り込み（filter_by_office ほか）各 Context に複製対象カラムが異なる
列挙の日本語ラベルdriver_live/labels.ex を新設リソースごとに分ける方針（repository-structure.md 3.2）
一覧・詳細・フォームのレイアウト共通コンポーネントを再利用すでに data_table 等に切り出し済み
LiveView の絞り込み処理（handle_event("filter", ...)）複製する対象パラメータとパスが異なる。3つ目で共通化を検討する

8. テスト方針

対象内容

9. リスクと対応

リスク対応
部分ユニークインデックスと unique_constraint の噛み合わせマイグレーションで where: "user_id IS NOT NULL" を指定し、changeset で同名の制約を宣言する。テストで二重紐付けを検証する
Scope.for_user/1 が preload 前提になり、既存のログイン処理が壊れるNotLoaded を nil として扱う。既存テスト（143件）が通ることを確認する
運転者コードの採番規則が未確定自動採番せず手入力とする。運用の規則が決まったら採番機能を別途検討する
免許種類の配列とフォームの噛み合わせチェックボックス群 + hidden の空値で「全解除」を表現する。テストで空配列がエラーになることを確認する
個人情報（免許証番号）の露出ログに出力しない。監査ログのDB記録のみとする
