2.2 alert_notifications

カラム内容
target_type / target_idvehicle / driver と対象ID（ポリモーフィックのため FK は張らない）
alert_type6種（inspection / liability_insurance / voluntary_insurance / periodic_3m / periodic_12m / license）
deadline_on / notify_stage期限日と段階（d60 / d30 / d7 / d0 / overdue）
notified_on通知日（JST）。下記の設計判断で追加
sent_at / status / error_message送信日時・sent / failed・失敗理由
設計判断 D-1：ユニーク制約に notified_on を加える
functional-design 4.3 のユニーク制約は (target_type, target_id, alert_type, deadline_on, notify_stage) だが、 これでは 7.2 の「超過は7日ごとに通知する」が実現できない（overdue は1行しか入らない）。 そこで制約を (target_type, target_id, alert_type, deadline_on, notify_stage, notified_on) とする。
d60 〜 d0 は残日数がその値になる日が1日しかないため、制約の強さは実質変わらない（同日再実行・Oban リトライの二重送信は従来どおり防げる）。 functional-design.md 4.3 / 7.2 を実装に合わせて更新する。

3. ドメイン層

3.1 Maintenance スキーマ

#ルール扱い
V-20category = inspection は next_scheduled_on（新しい車検満了日）が必須changeset でエラー
V-21category = periodic_3m / periodic_12m は next_scheduled_on が必須changeset でエラー

3.2 Maintenances Context

list_maintenances(scope, params)    # 期間・車両・区分・拠点で絞り込み、実施日の降順

warnings(scope, changeset)
count_maintenances_by_category(scope)

拠点は車両の配置拠点に従う（日報の V-14-3 と同じ考え方）。管理者が代理登録しても車両の拠点の記録になる。 管理者以外は自拠点の車両しか選べないため、validate_office_scope/2 で弾く。

設計判断 D-2：期限更新は Multi.run で記録と同一トランザクション（V-20・V-21）。
更新先は category で決まる（inspection → inspection_expires_on、periodic_3m → next_periodic_3m_on、 periodic_12m → next_periodic_12m_on）。それ以外の区分は車両を触らない。
編集時も同じ関数を通す。ただし区分が変わった場合に旧フィールドを戻すことはしない（巻き戻しの正解が決まらないため）。 編集で期限を直したいときは車両台帳から直接直す運用とし、画面にその旨を注記する。

3.3 Alerts Context

期限は車両・運転者の列を横断した仮想的な一覧である。実体テーブルを持たないため、 6本のクエリを union_all し、subquery で包んでから並べ替え・ページネーションする。 メモリ上で全件展開しないため、coding-rules 6章のページネーション要件を満たす。

# 1本ぶんのイメージ（車両の5種 + 運転者の1種を union_all する）
from v in Vehicle,
  where: v.status != :scrapped,
  where: not is_nil(field(v, ^column)) and field(v, ^column) <= ^horizon_date,
  select: %{
    target_type: type(^"vehicle", :string), target_id: v.id,
    target_name: v.plate_number, office_id: v.office_id,
    alert_type: type(^alert_type, :string), deadline_on: field(v, ^column)
  }
list_deadlines(scope, params)       # 一覧画面。残日数の昇順、Pagination
count_deadlines_by_urgency(scope)   # ダッシュボード用 %{overdue: n, within_30: n}
all_notifiable_deadlines(today)     # ジョブ用。スコープなし・全拠点
notified?(deadline, stage, today)   # 送信済み判定（7.2 手順3）
record_sent/record_failed           # 通知ログの upsert

取得結果は %CoreApp.Alerts.Deadline{}（値オブジェクト）に詰め替える。 Web 層とワーカーが同じ構造体を見るため、表示と通知で残日数の計算がずれない。

4. 非同期処理

ワーカー責務
DeadlineAlertWorker
queue: :alerts		 cron 0 22 * * *（UTC＝JST 07:00）。全拠点を走査し、段階に該当し、かつ未送信のものだけ AlertMailWorker をエンキューする。メールは送らない。最終試行で異常終了した場合は全管理者にエラー通知してから再raiseする
AlertMailWorker
queue: :mailers		 1アラート＝1ジョブ＝1通。宛先（対象拠点の運行管理者全員＋全管理者）を解決し、送信結果を alert_notifications に sent / failed で記録する。送信済みなら何もしない
設計判断 D-3：通知ログは「アラート1件＝1行」、宛先は1通の to にまとめる。
alert_notifications に宛先カラムが無く、ユニーク制約も宛先を含まないため。 「1通の失敗が全体を止めない」という architecture 4.3 の要求は、アラート単位でジョブを分けることで満たす。

冪等性は次の2重で担保する。① エンキュー前の notified? による送信済みスキップ　 ② alert_notifications のユニーク制約（on_conflict で上書き）。Oban のリトライで二重送信しない。

4.1 メール仕様（functional-design 7.3）

種別件名
期限前[車両管理] {拠点名} {対象名} の{期限種別}が残り{N}日です
超過[車両管理][超過] {拠点名} {対象名} の{期限種別}が期限切れです

本文に対象・期限種別・期限日・残日数と詳細画面の URL を入れる。URL は CoreAppWeb.Endpoint.url() と ~p で組み立て、文字列連結しない。

URL内容
/management/maintenances 一覧。キーワード（車両番号・業者）／期間／車両／区分／拠点（管理者のみ）で絞り込み。実施日の降順、50件ページング

配色は既存の <.deadline_badge> に揃える（超過=accent-orange-deep / 7日以内=accent-orange / 30日以内=accent-purple-deep / それ以外=無色）。 DESIGN-notion.md に定義済みのトークンのみを使い、新しい色は増やさない。

サイドナビの「点検整備・期限」を実装済みにし、点検整備一覧とアラート一覧の2項目に分ける。 ダッシュボードには運行管理者・管理者向けに「期限超過」「30日以内」のカードを追加する。 車両詳細の「履歴」プレースホルダを点検整備履歴（直近5件）に差し替える。
