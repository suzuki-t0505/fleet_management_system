2. ドメイン層

2.1 Offices

list_offices(scope, params)   # q（拠点コード・名称）/ active で絞り込み、コード昇順
all_offices()                 # 既存。有効な拠点のみ。他機能の選択肢用

all_offices/0 が既に active == true で絞っているため、拠点を無効化するだけで 車両・運転者・ユーザーの選択肢から外れる（R-2）。

設計判断 D-1：拠点の作成・更新は監査ログを取らない
PRD セキュリティの監査対象は「台帳の作成・更新・削除、ユーザー権限の変更、日報の承認・差戻し、 事故記録の全社共有設定」であり、拠点マスタは含まれない。
加えて、最初の拠点は操作者（管理者）が存在しない状態で作られる（seeds・フィクスチャ）。 ここで scope を必須にすると「拠点がないと管理者を作れず、管理者がないと拠点を作れない」循環になる。 そのため create_office/1 / update_office/2 は現在の形のまま据え置く。

2.2 Accounts

list_users(scope, params)            # q（氏名・メール）/ office_id / role / active、メール昇順
get_user_for_admin!(scope, id)       # office と driver を preload
register_user(scope, attrs, opts)    # 作成 + 監査ログ（create）
update_user(scope, user, attrs, opts)# 更新 + 監査ログ（role 変更時は role_change）
unlock_user(scope, user)             # ログイン失敗によるロックの解除

既存の create_user/1 と update_user_profile/2 は、認証プラミングと seeds・フィクスチャが使う低レベル関数として残し、管理者操作の入口を別名で足す。 これも D-1 と同じ循環（管理者を作るのに管理者が要る）を避けるため。

設計判断 D-2：ロール変更は role_change として記録する
audit_logs.action に既に role_change がある。1回の更新で氏名とロールが同時に 変わることもあるため、ロールが変わったかどうかだけで action を決める （変わっていれば role_change、それ以外は update）。変更差分は changes に入る。
設計判断 D-3：自分自身のロール変更・無効化を禁止する（R-7）
最後の管理者が自分を member にすると、誰も管理画面に入れなくなる。 Context の update_user/4 で scope.user.id == user.id のときにロール・有効フラグの 変更を拒否し、画面側でも該当項目を無効化する。Web だけの制御にしない （coding-rules 11章の多層防御）。

2.3 AuditLogs

既存の list_audit_logs/2 に action と q（操作者の氏名・メール）の絞り込みを足す。 操作者の選択肢はユーザー数だけ増えるため、セレクトではなくキーワード検索にする。

3. バリデーション

#ルール扱い
V-29拠点コードは全社で一意フォームにエラー表示
V-30拠点は物理削除しない。無効化で運用し、無効な拠点は選択肢に出さない削除ボタンを提供しない
V-31メールアドレスは全社で一意。管理者は編集画面で変更できない登録時のみ入力可。編集画面では読み取り専用
V-32管理者は自分自身のロール変更・無効化ができないContext で拒否し、画面でも入力を無効化
V-33無効化したユーザーはログインできない。記録は保持する実装済み（authenticate_user/2）

4. 画面

URL内容
/management/offices 一覧。キーワードと有効/無効で絞り込み。既定は有効のみ。コード昇順
/management/offices/new
/management/offices/:id/edit		 登録・編集。無効化はチェックボックス
/management/users 一覧。キーワード（氏名・メール）／拠点／ロール／状態で絞り込み。ロールと状態（有効・無効・ロック中）をバッジ表示
/management/users/new
/management/users/:id/edit		 登録・編集。編集ではメールアドレスを読み取り専用にし、ログインリンク送信とロック解除をこの画面に置く。自分自身の編集ではロール・有効フラグを無効化し、理由を注記する
/management/audit_logs 一覧。操作日時（JST）・操作者・操作・リソース種別・対象ID・変更内容。変更内容は key: 値 の行で表示する

登録直後にログインリンクを自動送信し、一覧へ「アカウントを発行し、ログインリンクを送信しました」と出す。 状態バッジは既存の <.status_badge> に :user 種別を足して使う（新しい色は増やさない）。 サイドナビの「ユーザー」「拠点」「監査ログ」を実装済みにする。

対象観点

Accounts登録・更新の監査ログ（create / update / role_change）、自分自身の変更の拒否、ロック解除、一覧の絞り込み
