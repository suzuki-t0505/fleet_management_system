.steering / 20260913-vehicle-registry

設計：車両台帳

要求内容は requirements.html。

1. 全体方針

  • 車両台帳を、以降の台帳画面の型（テンプレート）にする。一覧・詳細・フォームの構造と共通コンポーネントを、運転者台帳・点検整備でそのまま再利用できる形にする
  • 拠点の絞り込みはすべてクエリ層で行う。LiveView に office_id の条件を書かない
  • 他拠点のレコードは「権限エラー」ではなく存在しないものとして扱う（get_vehicle!(scope, id) が Ecto.NoResultsError → 404）。他拠点に何が存在するかを推測させないため
  • 監査ログは車両の保存と同一トランザクションで書く

2. データモデル

定義は functional-design.md 4.3 のとおり。列挙は Ecto.Enum、DBのカラム型は :string。

2.2 audit_logs

functional-design.md 4.3 のとおり。追記専用とし、更新・削除の関数を作らない。

user_id / action / resource_type / resource_id / changes(jsonb) / ip_address / inserted_at

updated_at は持たない（timestamps(type: :utc_datetime, updated_at: false)）。

3.2 スコープの適用

defp scoped(query, %Scope{role: :admin}), do: query
defp scoped(query, %Scope{office_id: office_id}),
  do: where(query, [v], v.office_id == ^office_id)

get_vehicle!/2 も同じ scoped/2 を通す。これにより他拠点のIDでは Ecto.NoResultsError になる。

3.4 ページネーション

coding-rules.md 4.3 は list_* の戻り値を %Scrivener.Page{} としているが、本プロジェクトは Scrivener を採用していない（architecture.md 4.2 で limit/offset 方式と決定）。 CoreApp.Utils.Pagination に同等の構造体を用意し、以降のすべての list_* で共通して使う。 
# lib/core_app/utils/pagination.ex
%CoreApp.Utils.Pagination{
  entries: [...], page_number: 1, page_size: 50, total_entries: 128, total_pages: 3
}

Pagination.paginate(query, params, repo)   # limit/offset と件数取得をまとめる

3.5 CoreApp.AuditLogs

record(scope, action, resource, opts \\ [])   # %Ecto.Changeset{} の変更差分を changes に保存
record_multi(multi, name, scope, action, fun) # Ecto.Multi に組み込む形
  • changes には changeset の changes（変更後の値）を保存する。更新時は変更されたキーのみが入る
  • パスワード等の機微情報を持つリソースは対象外（車両・運転者・拠点・ユーザー権限のみ）
  • IPアドレスは LiveView の connect_info から取得し、scope ではなくオプションで渡す
Ecto.Multi.new()
|> Ecto.Multi.insert(:vehicle, Vehicle.changeset(%Vehicle{}, attrs))
|> AuditLogs.record_multi(:audit_log, scope, :create, &{"vehicle", &1.vehicle})
|> Repo.transaction()

3.6 JSTの「今日」

期限の残日数計算に使うため、CoreApp.Utils.ConvertDatetime に以下を用意する（development-guidelines.md 6.2）。

today()                  # JSTの今日 (Date)
to_jst(utc_datetime)     # 表示用の変換
days_until(date)         # date - JSTの今日（負数は超過）

4.2 一覧画面（管理者・運行管理者）

  • ヘッダー右に「車両を登録」ボタン（button-primary）
  • 絞り込みバー：検索ボックス（車両番号・車名）／拠点セレクト（管理者のみ表示）／ステータス／車種区分／「廃車を含む」チェック
  • 絞り込みは phx-change で push_patch し、条件をクエリパラメータに保持する
  • テーブル列：車両番号 / 車名（メーカー） / 車種区分 / 拠点（管理者のみ） / ステータス / 車検満了日（残日数バッジ）
  • 行クリックで詳細へ遷移。モバイル（lg未満）はカード表示に切り替える
  • 0件のときは空状態（ex-empty-state-card）を表示し、登録への導線を置く

4.3 詳細画面

  • 見出しに車両番号、右に「編集」ボタン
  • カード1：基本情報（車名・メーカー・車種区分・車台番号・初度登録年月・拠点・ステータス）
  • カード2：期限（車検・自賠責・任意保険・法定点検）。残日数に応じて配色する
  • カード3：諸元（積載量・総重量・定員・燃料・所有区分・リース満了日・最終オドメーター）
  • カード4：備考
  • 履歴（運行日報・点検整備・事故ヒヤリ）は「各機能の実装後に表示されます」と明記した枠のみ

4.4 フォーム画面

  • セクション分け：基本情報 / 期限 / 諸元 / 備考
  • phx-change="validate" で即時バリデーション
  • 拠点セレクトは管理者のみ変更可能。運行管理者は自拠点を固定表示する
  • 編集時はステータスも変更できる（「廃車」への変更もここで行う。削除ボタンは置かない）
  • 375px で縦1カラム、横スクロールなし

4.5 一般利用者向け画面

  • 一覧は検索と車種区分の絞り込みのみ（拠点は自拠点固定、ステータスは稼働中・整備中・休車）
  • 詳細は基本情報と期限のみ。編集導線を一切表示しない

6. バリデーション（R-2）

#内容実装
V-1車両番号は全社で一意DBのユニーク制約 + unique_constraint。メッセージ「この車両番号は既に登録されています」
V-2各期限日は初度登録年月以降changeset で比較。4つの期限すべてに適用
V-3廃車は選択肢から除外他機能の実装時に all_selectable_vehicles/1 を使う。本作業では一覧の既定除外のみ
V-4物理削除しないdelete_vehicle を実装しない。UIに削除ボタンを置かない
追加初度登録年月は未来日不可、数値項目は0より大きいchangeset

7. 実装順序

  1. Utils.ConvertDatetime / Utils.Pagination（以降の全機能で使う土台）
  2. audit_logs テーブル + AuditLogs Context
  3. vehicles テーブル + Vehicle スキーマ + changeset（V-1〜V-2）
  4. Vehicles Context（スコープ・絞り込み・監査ログ付きCRUD）＋ Context テスト
  5. 共通コンポーネント（table / search / pagination / status / card）
  6. 管理者・運行管理者向け 一覧 → 詳細 → フォーム
  7. 一般利用者向け 一覧・詳細
  8. ルーター登録とナビゲーションの有効化
  9. seeds に車両データを追加 → 通し動作確認
  10. 永続ドキュメントの更新要否確認

各ステップの完了時に make check を実行する。

8. テスト方針

対象内容
スコープ境界運行管理者が他拠点の車両を get_vehicle!/2 で取得できない／一覧に出ない／更新できない。管理者は取得できる
changesetV-1（一意）・V-2（期限 >= 初度登録）・必須項目・数値の下限
一覧の絞り込み検索・ステータス・車種区分・拠点。既定で廃車が除外されること
ページネーション51件で2ページに分かれ、total_entries が正しいこと
監査ログ作成・更新で1件記録され、changes に変更後の値が入ること。失敗時は車両も記録も残らないこと
LiveView登録→一覧反映、編集→詳細反映、廃車→一覧から消える、重複車両番号でエラー表示
認可一般利用者が /management/vehicles でダッシュボードへ差し戻される。運行管理者が他拠点の詳細URLで 404
残日数days_until/1 が JST 基準で計算されること（UTCとの日付境界を含む）

9. リスクと対応

リスク対応
他拠点データの露出Context 関数が scope を必須で受け取る設計にし、境界テストを対で書く。LiveView 側で絞り込まない
共通コンポーネントの過剰設計車両台帳で実際に必要なものだけを作る。2つ目の台帳（運転者）で再利用するときに汎用化する
監査ログの記録漏れContext の CRUD 内で記録し、LiveView からは呼ばない。テストで件数を検証する
Ecto.Enum とフォームの噛み合わせセレクトの選択肢は Vehicle.statuses/0 等のモジュール関数から生成し、画面にベタ書きしない
日付の1日ずれ残日数は必ず Utils.ConvertDatetime.today/0（JST）を基準にする。Date.utc_today/0 を使わない
